# Phase 4.1: Realistic Test Fixtures - Research

**Researched:** 2026-02-07
**Domain:** Rust test architecture, NLP/readability test data, shared fixture patterns
**Confidence:** HIGH

## Summary

Phase 4.1 is a test infrastructure improvement phase that introduces realistic text fixtures across all modules (normalizers, tokenizers, diff, metrics, pipeline). The current codebase has 831 passing tests but uses predominantly synthetic/minimal test data: 2-4 word phrases ("the cat sat", "hello world", "cat dog"), manually constructed dependencies, and per-file duplicate helper functions. Readability metrics are tested with hand-computed values against dummy `ProcessedText` structs rather than actual text passages. Diff tests use synthetic token sequences rather than real document edit scenarios.

The standard Rust approach is to create a `tests/common/mod.rs` module containing shared fixture constants, helper functions, and builder utilities. This project already uses `test-case` (3.3) and `proptest` (1.6) as dev-dependencies, plus `insta` for snapshot testing -- no new dependencies are needed.

**Primary recommendation:** Create `tests/common/mod.rs` with (a) a curated library of public-domain/original text constants organized by category (simple, literary, technical, academic, multi-language), (b) shared helper functions replacing the 30+ duplicated `process()` / `make_text()` / `dummy_text()` helpers, and (c) realistic before/after document pairs for diff testing. Then enhance existing test files to import from `common` and add new test cases using these fixtures.

### Pattern 1: Shared Fixture Module (`tests/common/mod.rs`)

**What:** A single module exporting text constants, helper functions, and builder utilities.
**When to use:** Every integration test file that needs realistic text data.

The module should contain these sections:

```rust
// tests/common/mod.rs

use std::sync::Arc;
use redline_core::process::ProcessedText;
use redline_core::tokenize::WordTokenizer;
use redline_core::{ExecutionMode, TextProcessor};

// ── Text Constants: Simple (Flesch 90+, grade ~3) ────────────────────
pub const SIMPLE_PROSE: &str = "\
The cat sat on the mat. The dog lay on the rug. \
A bird sang in the tree. The sun was warm and bright.";

// ── Text Constants: Literary (Flesch 60-70, grade ~8) ────────────────
pub const LITERARY_PROSE: &str = "\
It was a bright cold day in April, and the clocks \
were striking thirteen. The hallway smelt of boiled \
cabbage and old rag mats.";
// NOTE: Must be original or public domain text

// ── Text Constants: Technical (Flesch 30-50, grade ~12) ──────────────
pub const TECHNICAL_PROSE: &str = "\
The algorithm employs a dynamic programming approach \
to compute the minimum edit distance between two sequences. \
Each cell in the matrix represents the optimal alignment \
cost up to that position, considering insertions, deletions, \
and substitutions.";

// ── Text Constants: Academic (Flesch <30, grade ~16) ─────────────────
pub const ACADEMIC_PROSE: &str = "\
The epistemological implications of computational linguistics \
necessitate a rigorous examination of morphosyntactic \
representations within probabilistic frameworks, particularly \
regarding the disambiguation of polysemous lexical items \
in context-dependent semantic analyses.";

// ── Helper Functions (replacing 30+ duplicates) ──────────────────────
pub fn process(s: &str) -> ProcessedText {
    TextProcessor::new(vec![], Box::new(WordTokenizer), ExecutionMode::All)
        .unwrap()
        .process(s)
        .unwrap()
}

pub fn process_arc(s: &str) -> Arc<ProcessedText> {
    Arc::new(process(s))
}
```

**How each test file uses it:**
```rust
mod common;

#[test]
fn readability_literary_passage() {
    let text = common::process(common::LITERARY_PROSE);
    // ...
}
```

### Pattern 2: Tiered Text Constants by Readability Level

**What:** Text fixtures organized by known approximate Flesch Reading Ease score bands.
**Why:** Readability tests (TFIX-05) need text with known grade levels to validate formulas produce sensible results. The project's syllable heuristic is ~90-95% accurate, so exact scores won't match published values -- but the *ordering* (simple < literary < technical < academic) must hold.

| Tier | Flesch RE Range | Grade Level | Characteristics |
|------|----------------|-------------|-----------------|
| SIMPLE | 90-100+ | K-5 | Monosyllabic words, short sentences |
| LITERARY | 60-70 | 6-8 | Mixed sentence lengths, 2-syllable words common |
| TECHNICAL | 30-50 | 9-12 | Domain terminology, longer sentences |
| ACADEMIC | 0-30 | 13-16+ | Polysyllabic jargon, complex syntax |

**Validation approach:** Assert `flesch(SIMPLE) > flesch(LITERARY) > flesch(TECHNICAL) > flesch(ACADEMIC)` rather than exact values. This is robust against syllable heuristic imprecision.

### Pattern 3: Realistic Diff Pairs

**What:** Before/after document text representing real editing scenarios.
**Why:** Current diff tests use "the cat sat" vs "the dog sat on the mat" -- not realistic editing. Real scenarios include:

### Anti-Patterns to Avoid

- **Copyrighted text in fixtures:** Do NOT copy passages from copyrighted books (Harry Potter, etc.). Use public domain (Project Gutenberg pre-1928) or write original prose.
- **Overly long fixtures:** Keep each fixture under ~500 bytes. Longer is not better for CI speed. A 3-4 sentence paragraph is the sweet spot.
- **Exact-value assertions for readability:** The syllable counter is heuristic (~90-95% accuracy). Asserting `flesch == 78.245` for real text is fragile. Assert ranges or orderings instead.
- **Fixture files on disk:** Don't use external `.txt` files that need `include_str!()` or runtime file I/O. Inline `const &str` compiles to the binary, is zero-cost, and can't break due to missing files.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Parameterized tests | Manual test function per variant | `test-case` macro | Already a dev-dep, generates named sub-tests |
| Shared process() helper | Copy-paste in every test file | `common::process()` | Currently duplicated 30+ times across files |
| Random Unicode input | Manual Unicode strings | `proptest` strategies | Already used; covers edge cases better |
| Snapshot readability values | Hand-computed expected values | `insta` snapshots | Already a dev-dep; captures full metric output |
| Public domain text sourcing | Writing text from scratch | Adapt from Project Gutenberg | Verified public domain, realistic prose styles |

## Common Pitfalls

### Pitfall 1: Syllable Heuristic Sensitivity
**What goes wrong:** Tests assert exact readability scores (e.g., `assert_eq!(flesch, 65.3)`) against real text, but the syllable counter uses a vowel-group heuristic that's ~90-95% accurate. Words like "created" count as 2 syllables (heuristic) instead of 3 (actual).
**Why it happens:** The `count_syllables()` function in `syllable_count.rs` uses vowel groups + silent-e rules. It fails on irregular English words.
**How to avoid:** Use inequality/ordering assertions: `flesch(simple) > flesch(academic)`. For range assertions, use wide bands (e.g., `50.0..90.0` for literary prose). Never assert exact Flesch values for multi-word text.
**Warning signs:** Flaky tests that fail when fixture text is slightly modified.

### Pitfall 2: SentenceTokenizer Span Reference Frame
**What goes wrong:** Tests assume all token spans reference original text positions. SentenceTokenizer spans reference NORMALIZED positions (not original).
**Why it happens:** This is a known design tradeoff documented in project memory. WordTokenizer and CharTokenizer map through CharMapping; SentenceTokenizer does not.
**How to avoid:** When writing fixture tests for SentenceTokenizer, assert spans against `result.normalized.len()`, not `input.len()`. The existing `assert_sentence_pipeline_valid()` helper in `normalizer_tokenizer_matrix.rs` shows the correct pattern.
**Warning signs:** Span-end-exceeds-length panics in tests using SentenceTokenizer with normalizers.

### Pitfall 3: WordTokenizer Punctuation Attachment
**What goes wrong:** Tests assume punctuation is a separate token. WordTokenizer attaches punctuation to words ("hello," is 1 token, not 2).
**Why it happens:** Design decision documented in project memory: "punctuation stays with words."
**How to avoid:** When counting expected words from fixture text, count punctuation-attached words. "Hello, world!" has 2 tokens: "Hello," and "world!" -- not 3.
**Warning signs:** Token count assertions off by the number of punctuation marks.

### Pitfall 4: Copyright Contamination
**What goes wrong:** Copyrighted text gets committed as test fixtures. This creates legal risk.
**Why it happens:** It's tempting to copy a paragraph from a famous book as a "known readability level" fixture.
**How to avoid:** Only use: (a) original prose written for this project, (b) text from Project Gutenberg (pre-1928 US publication), or (c) well-known public domain sentences like "The quick brown fox." Each fixture constant should have a comment documenting its source.
**Warning signs:** Recognizable passages from post-1928 works.

### Pitfall 5: Test File Compilation Overhead
**What goes wrong:** Each file in `tests/` compiles as a separate crate. Adding many new test files slows CI.
**Why it happens:** Rust's integration test model creates one binary per `tests/*.rs` file.
**How to avoid:** Don't create new test files. Enhance existing ones by adding new test functions that use `common` fixtures. The `common/mod.rs` pattern only compiles once per test binary that uses it.
**Warning signs:** `cargo test --no-run` time increasing significantly.

### Pitfall 6: Empty Input Normalization
**What goes wrong:** Passing empty string to normalizers causes `NormalizeError::EmptyInput`.
**Why it happens:** All normalizers reject empty input. `WhitespaceNormalizer` also rejects all-whitespace input.
**How to avoid:** Test fixtures must be non-empty. When testing "edge case" scenarios near empty, use minimal non-empty strings like "a" rather than "".
**Warning signs:** `unwrap()` panics on `process("")` calls.

## Code Examples

### Example 1: Using common fixtures in readability tests

```rust
// tests/metrics_integration.rs (enhanced)
mod common;

#[test]
fn readability_ordering_across_difficulty_levels() {
    let mut reg = MetricRegistry::new();
    register_builtins(&mut reg).unwrap();
    let engine = MetricsEngine::new(reg);

    let simple = common::process(common::SIMPLE_PROSE);
    let literary = common::process(common::LITERARY_PROSE);
    let technical = common::process(common::TECHNICAL_PROSE);
    let academic = common::process(common::ACADEMIC_PROSE);

    let fre_simple = engine.get("flesch_reading_ease", &MetricInput::Single(&simple))
        .as_float().unwrap();
    let fre_literary = engine.get("flesch_reading_ease", &MetricInput::Single(&literary))
        .as_float().unwrap();
    let fre_technical = engine.get("flesch_reading_ease", &MetricInput::Single(&technical))
        .as_float().unwrap();
    let fre_academic = engine.get("flesch_reading_ease", &MetricInput::Single(&academic))
        .as_float().unwrap();

    // Higher FRE = easier to read
    assert!(fre_simple > fre_literary, "simple ({fre_simple}) should be easier than literary ({fre_literary})");
    assert!(fre_literary > fre_technical, "literary ({fre_literary}) should be easier than technical ({fre_technical})");
    assert!(fre_technical > fre_academic, "technical ({fre_technical}) should be easier than academic ({fre_academic})");
}
```

### Example 3: Normalizer test with realistic paragraph

```rust
// tests/text_processing.rs (enhanced)
mod common;

#[test]
fn full_pipeline_realistic_paragraph() {
    let processor = TextProcessor::new(
        vec![
            Box::new(Lowercase),
            Box::new(WhitespaceNormalizer),
            Box::new(UnicodeNormalizer::default()),
        ],
        Box::new(WordTokenizer),
        ExecutionMode::All,
    ).unwrap();

    let result = processor.process(common::TECHNICAL_PROSE).unwrap();

    // Realistic paragraph should produce many tokens
    assert!(result.tokens.len() > 20, "got {} tokens", result.tokens.len());

    // All tokens should resolve
    for token in &result.tokens {
        assert!(result.text_store.resolve(token.text_id).is_ok());
    }

    // Normalized text should be lowercase
    assert_eq!(result.normalized, result.normalized.to_lowercase());

    // CharMapping should be valid
    let mapping = result.composed_mapping.as_ref().unwrap();
    assert_eq!(mapping.original_len() as usize, common::TECHNICAL_PROSE.len());
}
```

## Fixture Content Guidelines

### Text Sources (Legal Safety)

| Source | Status | Use For |
|--------|--------|---------|
| Original prose (written for this project) | SAFE | All fixtures |
| Project Gutenberg (pre-1928 US pub) | SAFE | Literary/academic style samples |
| US government documents | SAFE (public domain) | Technical/formal style |
| Wikipedia (CC BY-SA) | SAFE with attribution comment | Factual/encyclopedic style |
| Post-1928 books | UNSAFE | Never use |
| Song lyrics | UNSAFE | Never use |

### Recommended Fixture Sizes

| Category | Size | Rationale |
|----------|------|-----------|
| Simple phrases | 5-15 words | Unit test assertions |
| Short paragraphs | 2-4 sentences, 30-60 words | Readability, diff, pipeline |
| Multi-paragraph | 2-3 paragraphs, 80-150 words | Paragraph count, line count metrics |
| Maximum size | ~500 bytes | CI speed; larger provides diminishing returns |

### Key Fixture Requirements

1. **Every tier needs sentence-ending punctuation** (`.`, `!`, `?`) -- the `SentenceCountMetric` counts these. Text without enders produces `sentence_count = 0`, which triggers divide-by-zero guards in readability metrics (returning 0.0).

2. **Academic fixtures need polysyllabic words** -- Gunning Fog and SMOG metrics count words with 3+ syllables. Academic text should have 40%+ polysyllabic words to produce meaningfully different scores from simple text.

3. **Diff pairs must share some tokens** -- For `similarity_ratio` to be meaningful, before/after text needs overlapping vocabulary. A complete rewrite (0% overlap) just tests the degenerate case.

4. **Multi-language text needs spaces for WordTokenizer** -- CJK text without spaces produces 1 token per whitespace-delimited chunk. This is correct behavior but must be accounted for in assertions.

## Open Questions

1. **Should `common/mod.rs` also expose builder-style helpers for constructing ProcessedText with specific token counts?**
   - What we know: Several metrics unit tests manually construct `ProcessedText` with empty tokens and hand-injected dependencies. This pattern is intentional for isolated unit testing.
   - What's unclear: Whether to consolidate these into `common` or leave them in-file (they serve a different purpose than integration fixtures).
   - Recommendation: Leave metric unit test helpers in their respective source files. Only consolidate the integration test `process()` helper and text constants into `common`.

2. **Should existing constants in `normalizer_tokenizer_matrix.rs` be moved or duplicated?**
   - What we know: 7 constants exist in `normalizer_tokenizer_matrix.rs` that could be shared.
   - Recommendation: Move them to `common/mod.rs` and update `normalizer_tokenizer_matrix.rs` to `use common::*`. This avoids duplication and establishes the single-source pattern.

3. **How to handle the SentenceTokenizer span difference in shared fixtures?**
   - What we know: SentenceTokenizer spans reference normalized positions. Other tokenizers reference original positions.
   - Recommendation: The `common` module should document this clearly. Helper functions can include a `process_for_sentence()` variant if needed, or tests can simply account for it.
